# UX-18 — Arabic messages that open with a number — Evidence

- Date: 2026-10-11
- Status: **done**
- Card approved in the clean-up batch ("approved for all 6"). No API change.

## The fault

The layout runs left to right in both languages (ADR-012). In a left-to-right line, an Arabic
string that OPENS with a number is drawn with the number at the LEFT of the words. An Arabic
reader starts at the right, so the number arrives last: «8–14 يومًا» read as "days 14–8… 8".

Measured on the People screen's summary, with `Range.getBoundingClientRect()` on each piece
(reading a screenshot proved unreliable — see Landmines):

| | "8" | "14" | the word «يومًا» |
|---|---|---|---|
| Before | x 564–572 | x 578–591 | x 594–612 |
| After | x 604–612 | x 586–598 | x 564–582 |

Before, the number sat at the left end. After, the word is at the left, the number at the right
— where an Arabic line starts — and the range reads right to left, as ranges inside Arabic
sentences already did.

## The fix: in the message, not at each call site

DEP-03 fixed one such line by wrapping it in `<span><bdi>…</bdi></span>`. Doing that everywhere
means finding about a hundred call sites and remembering it for every new one.

Instead the message carries a **right-to-left mark** (U+200F) before the number. The mark is
invisible and has no width; it makes the number part of the Arabic run. It is written in
`ar.json` as the escape ``, so a reviewer can see it.

- **201 marks** in **108 messages** (a plural or select message takes one per branch).
- Marked: every Arabic message, or branch, that starts with a digit, `#`, or a `{placeholder}`
  (a placeholder may hold a number, a date or a Latin name; if it holds Arabic text the mark
  changes nothing).
- English is untouched.

## The guard

`apps/web/scripts/verify-ar-messages.mjs`, run by `pnpm lint` for the web app
(`"lint": "eslint src && node scripts/verify-ar-messages.mjs"`). It fails when:

1. an Arabic message or branch opens with a number or placeholder and has no mark;
2. the mark appears as a literal character — an invisible character cannot be reviewed.

| Proof | Result |
|---|---|
| Remove one mark (`nav.countRequests`) | Fails, names the key: `nav.countRequests: "# طلبات بانتظار المعالجة"`; `pnpm lint` exits 1 |
| Replace one escape with the literal character | Fails (exit 1) |
| Restored | Passes |

The guard script first held two literal marks itself (its own constant and a comment). Caught
on review and replaced with escapes; the script is now plain ASCII apart from its Arabic
example.

## Found, not fixed → UX-20

1. **A full stop at the wrong end.** An Arabic sentence that ENDS in a full stop, outside a
   `<bdi>`, shows the stop at its START (measured on the Fees tab: first word x 495–528, the stop
   at x 528–532). A mark after the final punctuation would fix it in the data, the same way.
2. **A Latin name inside an Arabic sentence** (the Leaves summary ending "…من PEOPLE&GRO")
   splits the line into pieces laid out left to right. That one needs `<bdi>` at the call site.
