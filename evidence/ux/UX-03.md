## The problem this card exists to solve

Every list in the app had **no search, no sort and no paging**. With a real dataset
the only way to find a record was Ctrl-F over a fully rendered table — and
Employees, the primary entity, was the worst case.

And a search box alone would have made things *worse*, which is the part worth
dwelling on.

## `@hr/text` — why a whole package for a string function

Measured before writing anything:

```
'أحمد حسن'.includes('احمد')  →  false
'إدارة'.includes('ادارة')     →  false
'إجازة'.includes('اجازه')     →  false
'مصطفى'.includes('مصطفي')     →  false
```

All four are the **ordinary way people type those words** — the hamza on an alef is
routinely dropped, `ة`/`ه` are interchangeable at word end, `ى`/`ي` get swapped. A
naive search matches by UTF-16 code unit, so the record doesn't rank low, it
**vanishes**. On a product whose default language is Arabic, that is worse than
having no search box: it fails silently and the user concludes the record isn't
there.

`toLowerCase()` does nothing (Arabic has no case). `Intl.Collator` can *compare*
but not *transform*, so it can't feed a substring match — and it misses alef madda
and teh marbuta anyway. `NFKC` alone fixes nothing. So: an explicit fold mirroring
Lucene's `ArabicNormalizer` (what Elasticsearch's `arabic_normalization` uses) plus
digit folding.

**A shared package, not a web util**, because when server-side search lands it must
use the *same* fold — otherwise the client and the API disagree about what matches,
which is a miserable bug to chase. Mirrors `@hr/dates` exactly, so no new pattern.

### Tests — 18, and they assert the naive behaviour too

`packages/text/src/index.test.ts` asserts both sides of every case:

```ts
expect(data.includes(query)).toBe(false);      // what we would have shipped
expect(matchesSearch(data, query)).toBe(true); // what we ship
```

Keeping the `false` assertion means if someone later "simplifies" the normaliser
away, the tests fail loudly rather than the search quietly returning nothing.

Also covered: idempotency, whitespace collapse, invisible bidi controls, Latin case
and accent folding (free from the `NFKD` + `\p{M}` step), empty query matches all,
**genuine non-matches still fail** (a fold that matches everything would be worse
than none), and one deliberate non-fold — `ؤ`/`ئ` → `ء` is *not* applied, because
Lucene doesn't and it over-merges distinct words.

## The DataTable

Hand-rolled rather than adopting a table engine: the API returns complete arrays
today, so this is sorting, filtering and slicing an array. If server-side
pagination lands, that is the moment to revisit — not before.

Choices taken from the research:

| Decision | Why |
|---|---|
| 40px rows, 14px text | the density every design system that publishes one converges on |
| Numeric columns end-aligned, `tabular-nums` | digits line up; proportional figures make right-aligned columns visually ragged |
| **Row actions always visible** | hidden controls measured a >20% drop in discoverability, and hover doesn't exist on the tablets used in a back office |
| Offset pagination **with a real total** | "312 employees" is frequently the answer the person came for; cursors cannot show it |
| Sortable headers are real `<button>`s with `aria-sort` | and only one column carries it at a time, which is also why multi-sort isn't offered |
| Empty ≠ no-results | a filtered miss offers **clear filters**; a genuinely empty list offers create. Never a create CTA to someone who just filtered |
| Search resets to page 1 | a new query must not leave you on page 4 of 1 |
| Sorts on raw values, not rendered text | `hireDate` sorts on the ISO date — sorting the dual-calendar display string would order by Hijri month *name* |

### One thing the verification exposed that isn't a bug

Searching `محاسب` (accountant, in Arabic) returned nothing. I checked the data
rather than assuming: **`job_title_ar` is empty for three of the four seeded
employees** — only English titles exist. The search is correct; the seed data is
thin. That is exactly what UX-07 is for, and it's a second data point for why
realistic demo data is a prerequisite rather than polish.

## Adoption re-scoped, deliberately

The card said eight screens. I adopted **one** (Employees) and am re-planning the
remaining seven as **UX-03c**.

Reason: each adoption is a careful rewrite that has to preserve that screen's
filters, row actions and permission gating. Eight of those in one commit is a large
diff with real regression surface and no way to verify each properly in one pass.
One reference adoption on the hardest screen proves the component; the rest become
a mechanical sweep that can be reviewed screen by screen.

Flagging it rather than quietly doing less — the card's DoD said eight, and this is
one.

## Two self-inflicted problems worth recording

1. **I wrote literal invisible bidi characters into the normaliser's regex** — in
   the very file whose comment says to use `\u` escapes so the source survives
   editors that mangle bidi text. `no-irregular-whitespace` caught it. Now escaped.
2. **The dev server predated the workspace link**, so `@hr/text` resolved for `tsc`
   but not for the running Next server — a module-not-found in the browser while
   typecheck was green. Restarting the dev server fixed it; worth knowing, because
   the two tools disagreeing looks alarming for a moment.
