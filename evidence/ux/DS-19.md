## What changed

### API

| File | Change |
|---|---|
| `@hr/contracts` `role.ts` (new) | `roleListResponseSchema`: `{ permissions: string[], roles: [{ id, kind, permissions, accounts }] }`; exported from the index |
| `modules/auth/api/roles.controller.ts` (new) | `GET /roles`, behind **`staff-user.read`** (Administrator + Auditor, so no new permission). Returns `PERMISSIONS` and `ROLE_PERMISSIONS` as they are, each role's kind, and its count of **active** accounts. Nothing editable |

**`test/roles-api.e2e-spec.ts` (new, 4 cases):**
1. The response keys are exactly `permissions` and `roles`. `permissions` equals `PERMISSIONS`; the role ids equal `ROLE_PERMISSIONS`' keys, in order. Each role's keys are exactly `accounts`, `id`, `kind`, `permissions`, and its permissions equal the code's bundle. Kinds: four staff, client, employee.
2. The account counts equal the database's active counts. The database is read before and after the API call, and only roles whose count didn't move are compared, because other specs create and delete helper accounts concurrently. At least 3 roles must qualify.
3. A disabled account is not counted (retried until the count holds still), and a disabled GRO officer does exist.
4. HR officer, GRO officer, client manager and employee get **403**; anonymous gets **401**.

**Proven red first:** all 4 failed with `404 Not Found` before the controller existed.

**Deviations from the prototype, kept on purpose:**
- **The matrix is the real one, not the prototype's 9 × 4.** The prototype's matrix is 9 coarse resources × Read/Write/Create/Delete. Ours is 24 resources and 70 permissions, with actions that are none of those four (approve, process, read-all, export, invite…). Each cell shows every action the resource has, dark when granted. The four familiar actions keep the prototype's icons; the rest are short labels, each with a full name (e.g. "Approve · Open roles · HR officer: granted").
- **Two capabilities are left out of the matrix and the counts:** `example` and `scope-check`, the walking skeleton's test capabilities.
- **Role cards count Read / Write / Create / Delete / Granted from the real bundles.** Write = `update` or config's `write`. Granted = all shown permissions.
- **No "Resend invitation".** Staff accounts are created with an initial password, not invited; the button reads **Add a user**.
- **No "Remove user".** Accounts are deactivated, never deleted, because sessions and the audit trail point at them (UX-10b). Deactivating ends the account's sessions (SS-06a).
- **Your own row is locked.** The server already refuses changing your own role or status; the role control and Deactivate are disabled there, with that reason as their title.
- **A two-factor line sits under each status.** It was a column on the old screen, and it matters to an Administrator because admin roles must enrol.
