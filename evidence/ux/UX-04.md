## What shipped

The product had **no home screen**. Login dropped you into a list — `/clients` for
most staff, `/audit` for admins — and the root URL still rendered the WS-01 walking
skeleton demo (a hardcoded sample company, today's Hijri date, a link to a
component-check page, and no way into the app).

Now:

- **`(app)/today`** — an urgency-ordered work queue.
- **The root URL redirects there.** The `(app)` guard already bounces
  unauthenticated visitors to `/login`, so the route needs no session check of its
  own.
- **Post-login lands there** for staff (client reps still land on the portal, their
  only surface).
- **"Today" is the first nav item**, hidden for client reps.

## The model: a work queue, not a dashboard

The objects in this product are **work items with owners and deadlines**, not
streaming measurements — so the right shape is closer to Linear's "My Issues" than
to a monitoring dashboard. Sections in urgency order (Overdue → Due today → This
week → Coming up), and **a section appears only when it has something in it**: an
empty section is noise, and a page of them reads as broken.

**It adds no data.** `/calendar/view` already merges own events with active Task,
Request and GRO deadlines, each source gated by its own read permission; this
re-projects that by urgency instead of by day, and adds expiring documents for
`document.read` holders.

### No KPI tile strip, deliberately

The mockup you reviewed had a metric strip with sparklines. I did not build it, and
the reason matters: the rule I committed to is that a metric earns its place only
with **a baseline, a direction, a threshold and a click-through**. There is no
history table in this system, so a baseline and a trend would have to be
**invented** — and a fabricated sparkline on a compliance screen is worse than no
sparkline.

What survives that test is a threshold-native count that opens the rows behind it,
so the counts live in the section headers where they are already clickable. A real
metric strip needs a snapshot mechanism, which is a Reporting decision rather than
a home-screen one. Flagging it rather than quietly shipping the mockup's tiles with
made-up numbers.

## Role-awareness, measured

Not asserted — probed live per role, counting what each actually receives:

| Role | Items by kind | Expiring docs |
|---|---|---|
| **gro_officer** | `gro: 2`, `request: 3`, `event: 1` | 1 |
| **finance** | `request: 3` — **no GRO, no recruitment** | 1 |
| **recruiter** | `request: 3`, `event: 1` — **no GRO** | 1 |

Finance and Recruiter are excluded from GRO by the permission matrix, and that
exclusion flows straight through `/calendar/view` to this page. So Finance gets a
genuinely **shorter** page rather than four permanently empty sections — which was
the strongest argument for role-based defaults in the first place.

## Two defects found and fixed while verifying

**1. Raw API enums were about to ship on the most-read screen.** `/calendar/view`
returns untranslated statuses, and for GRO items it uses the process **type** as the
title — so `iqama_renewal` appeared as a headline and `in_progress` as its status,
in Arabic. Fixed by reusing the label maps each domain screen already owns
(`gro.type.*`, `gro.status.*`, `requests.status.*`, `tasks.status.*`,
`documents.category.*`) rather than inventing a third vocabulary. Now reads
`تجديد إقامة · قيد التنفيذ`. Each lookup falls back to the raw value, so a new
server-side enum shows up as itself instead of crashing the page.

**2. Scaffolding strings were shipping in every page's HTML.** After the redirect
landed, `/en` still contained "Walking skeleton" — because next-intl serialises the
**whole** messages object to the client, and the now-dead `home` namespace was still
in it. Removed from both locales; verified the strings are gone from the payload.
Small, but it means the phrase was in the HTML of every page in the product.

## One thing I chose not to fake

There is no greeting by name. `/auth/me` returns a userId and a role but **no
display name**, because there is no staff-user directory yet (the same gap that
makes the Tasks table show a truncated UUID for assignees — UX-10). Deriving a name
from an email local-part would be inventing data, so the header shows the
dual-calendar date and the **role**, which is honest and actually useful: it tells
you which slice of work the page is showing.
