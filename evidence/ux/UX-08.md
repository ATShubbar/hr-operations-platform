# UX-08 — the Arabic typeface (and the bidi work that was actually justified) — Evidence

- Date: 2026-07-25
- Task card: `BACKLOG.md` → UX-08
- Status: done
- Commit: `UX-08: an Arabic typeface, and bidi isolation where it is needed`

## The finding

The app loaded `Inter({ subsets: ['latin'] })` and nothing else. **Inter has no
Arabic glyphs.** Measured on a real screen before touching anything:

```
Latin  in "Inter"  177.41px   vs serif 156.42px    → Inter really applied
Arabic in "Inter"  156.49px
Arabic in sans-serif 156.32px
Arabic in serif    154.99px                        → all three identical
```

Three different families producing one width, because all three resolved to the
same OS fallback. The product's **default locale had no chosen typeface** — it
rendered in Geeza Pro here, Tahoma on Windows, Noto Naskh on Android. After UX-07
put roughly ten times more Arabic on screen, that stopped being academic.

## What shipped

**IBM Plex Sans Arabic**, self-hosted through `next/font/google`, chosen to sit
beside Inter: both neo-grotesques with a similar vertical proportion, so the
mixed Arabic/Latin runs this product is full of — `Iqama — أحمد حسن`,
`محلل مالي · JO` — do not read as two typefaces arguing.

**One stack, not a locale switch:**

```css
--font-sans: var(--font-latin), var(--font-arabic), ui-sans-serif, system-ui, sans-serif;
```

The browser's per-character fallback already does the routing. No conditional
CSS, nothing to forget on a new screen.

## The trap that made this a three-attempt fix

Composing the stack was not enough. Measured after the first attempt:

```
app stack 482.41px   |   Plex 500.95px   |   OS sans 479.77px   → matched NEITHER
```

`next/font` emits **two** families per font: `Inter` and a generated
`"Inter Fallback"` — a local face (Arial) with `size-adjust` applied to match
Inter's metrics. Both land in the variable, so `var(--font-latin)` expanded to
`Inter, "Inter Fallback"` — and that generated fallback is a real system font
that **covers Arabic**. It intercepted every Arabic glyph before the stack ever
reached Plex.

Setting `adjustFontFallback: false` fixed that — and my first replacement,
`fallback: ['ui-sans-serif', 'system-ui']`, re-created the same trap one line
later, because generic families also resolve to faces with Arabic. Inter now
contributes only itself; the generics live once, at the end, after the Arabic
face.

**Proof it is now applied** (space-free word, so no cross-family space glyph
skews the measurement):

```
app stack 129.86px  ==  forced "IBM Plex Sans Arabic" 129.86px
OS sans   106.73px      Plex's metric fallback 99.87px
```

Latin unchanged: `312.23px` app stack == `312.23px` forced Inter.

## Weights

`font-medium` (500) appears 39 times in the UI and `font-semibold` (600) 40
times. Loading only 400/600 would have left every Arabic *medium* resolving down
to 400 while its Latin neighbour sat at 500 — a mismatch inside one line. Three
weights load, and each is a real face rather than a synthesised one:

```
400 → 129.86px      500 → 134.27px      600 → 136.99px
```

Nothing uses `font-bold`, so 700 is not loaded.

**Cost, measured rather than estimated:** an Arabic page downloads ~117KB of
Arabic outlines (three weights) on top of Inter's ~33KB, first visit only.
`display: swap` keeps text visible throughout.

**Layout shift: 0.0000** (`layout-shift` PerformanceObserver, buffered, over a
full load).

## The bidi work — much smaller than the backlog assumed

I measured the assumed problems before scheduling work on them, and most did not
exist:

| Assumption | Measured | Action |
|---|---|---|
| Dual-calendar dates reorder in RTL | Hijri paints right of Gregorian — **correct** | none |
| Hyphenated codes (`WP-2024-118`) reorder | identical isolated vs inherited — the strong-LTR prefix sets the run | none |
| Digits inconsistent | **457 Latin, 0 Arabic-Indic** — a real convention, already consistent | none |
| Identifier fields inherit RTL | **real** | fixed |

What was genuinely wrong: `TextField`'s prop was typed **`dir?: 'rtl'`** — it
could not express LTR *even in principle*, so every government identifier input
(iqama, national id, border, passport, work permit, GOSI registration, Absher
ref) and the IBAN inherited the page's RTL in the Arabic form. The type now
admits both, those eight fields are LTR, and the read-only `mono` identifier
display wraps its value in `<bdi dir="ltr">`. Verified on a real record:

```
bdi "2000012000"  dir=ltr  computed=ltr
bdi "WP-000012"   dir=ltr  computed=ltr
```

`٥ أيام`) while the entire app renders Latin digits. Mine to fix; now `8` and `5`.
