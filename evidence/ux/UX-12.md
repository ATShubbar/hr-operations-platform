# UX-12 — the Company column and filter on Employees — Evidence

- Date: 2026-07-25
- Task card: `BACKLOG.md` → UX-12
- Status: done
- Commit: `UX-12: Employees gains a Company column and a filter beside the search`
- Scope: `apps/web` only. **No API change** — `GET /employees?clientId=` already existed
  (`employees.controller.ts:51`, still the only list controller that accepts it).

## The gap

Employees was the **only cross-client list with neither a client column nor a client
filter**, while its own subtitle read *"Employee records across all client companies."*
Documents, requests, tasks, vacancies and GRO all had both.

## Two deliberate differences from the five screens that already had this

1. **The filter sits beside the search, not in a form above the table with an Apply
   button.** `DataTable` has had a `filters` slot since UX-03, documented as *"rendered
   before the search box"* — with **zero consumers**. This is its first. Dropping Apply
   means the list narrows on selection; the Select *is* the action.
2. **Server-side, not client-side.** Selecting a company refetches with `?clientId=`.
   The endpoint is unpaginated, so filtering in the browser would mean shipping every
   employee in the consultancy in order to hide most of them.

That leaves Employees looking slightly different from the other five. Deliberate: better
to prove the shape on one screen than sweep six uninvited. Converting the rest is its own
card.

## Measured

**The column**, `hr_officer`, English then Arabic:

```
Name▲ | Company↕ | Nationality↕ | Job title↕ | Status↕ | Hire date↕
الاسم▲ | الشركة↕ | الجنسية↕ | المسمى الوظيفي↕ | تاريخ التعيين↕

first row → Abdullah Alqahtani | Alpha Trading Co. | SA | Support Engineer | Active | …
```

Sortable and searchable, like every other column.

**The filter**, selecting *Gulf Medical Group*:

```
before   Showing 1–25 of 39
request  /api/employees?clientId=c1000000-0000-4000-8000-000000000004     ← exactly one
after    Showing 1–7 of 7      distinct companies in the Company column: ["Gulf Medical Group"]
trigger  "Gulf Medical Group"
```

Cross-checked against the database — Gulf Medical Group has exactly 7 employees.

**Arabic search on the company name.** The whole reason `@hr/text` exists: typing the
company without its hamza still finds it.

```
query  الالف
→ 12 rows, all شركة الألف التجارية
'شركة الألف التجارية'.includes('الالف')  →  false
```

A plain `includes()` returns nothing for that query. The column feeds both `name.ar` and
`name.en` into `searchValues`, so it works in either language whichever way the row is
rendered.

**The empty-vs-no-results split.** No seeded client has zero employees, so a temporary
one was inserted, the state observed, and the row deleted (verified: 5 clients before and
after).

```
filter → "Empty State Test Co."
→ "No matches — No records match your search or filters."  +  [Clear filters]
   NOT the first-run "no employees yet" state
[Clear filters] → /api/employees (no query string) → Showing 1–25 of 39, trigger "All companies"
```

This is what `filtersActive` is for — added in UX-03c precisely so a server-side filter
cannot make the table show a create CTA to someone who has just filtered.

**The risk in the card did not materialise.** A sixth column at 375px:

```
page overflow: 0px
table region:  scrollWidth 828 / clientWidth 341, tabIndex 0   (keyboard-reachable, UX-11)
filter wraps below the search (y 220 vs 176) and stays inside the viewport
```

## Also changed, because the column forced it

Clients were previously fetched **only when the create dialog opened**, and filtered to
`active`. The column needs them on first paint, and needs archived ones too — an archived
company's employees still have to render a name. So the list now loads unfiltered on
mount, and the *active-only* narrowing moved to the create picker, where it belongs: you
should not be able to hire into an archived company.

A failed client fetch is non-fatal by design — the column degrades to a short id and the
filter is empty, rather than the screen failing over a label lookup.

## Landmine found

**Editing `messages/*.json` while the dev server runs updates the server render but not
the client bundle**, and the failure is quiet: the server HTML contained `All companies`
while the browser rendered **`All`**, with `MISSING_MESSAGE: employees.filterAllClients`
only in the console. It reads as a *wrong translation*, not a missing one — I went
looking for a duplicate key before checking the console. A dev-server restart fixes it.
Same family as the UX-03 landmine (a newly-linked workspace package needs a restart).
