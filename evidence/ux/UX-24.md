# UX-24 — Lines joined by something other than a dot — Evidence

- Date: 2026-10-11
- Status: **done — measured, one fault found and fixed**
- The card said "measure first, then decide". Measurement reported, then the one-line fix
  approved ("approved"). No API change.

## The question

UX-22 fixed lines whose pieces are joined by a dot. Are lines joined by a dash, a slash, a colon,
brackets — or just a space between two elements — out of order too?

## Measured on screen

A third script: for every line whose text is built from more than one piece (any separator),
check by glyph position that each piece starts to the left of the one before it.

| Arabic view, Administrator, 1100px | Result |
|---|---|
| Screens swept | 26 (the usual 23 plus the Person record's Open work tab and Settings' other two tabs) |
| Lines built from several pieces | 14 |
| … out of order | **0** |

There are so few such lines because UX-22 turned most assembled lines into a single piece of
text; those are covered by the UX-20 sweep, which checks word order inside a piece whatever the
separator: 0 real faults.

## Read in the code

Every place in the web app that joins values with one of these separators:

| Separator | Places | What they are |
|---|---|---|
| Dash | 13 | 9 screen-reader labels (never drawn) · 4 date ranges, an Arabic date at each end — measured in order |
| Slash | 8 | 7 web addresses, not text · 1 count ("2/3") |
| Brackets | 1 | Arabic inside Arabic, already inside a `dots()` line |
| Colon | 3 | 2 join Arabic to Arabic · **1 joins an Arabic label to a raw value** |

## The one fault

Settings → System → per-client settings: each setting shows «القيمة السارية: "dual"» (effective
value). The section appears only after a company is picked, so no sweep had seen it. With a
company picked:

| «القيمة السارية: "dual"» | label | colon | value | Read from the right |
|---|---|---|---|---|
| Before | x 32–94 | x 94–98 | x 101–137 | the value, then its label |
| After | x 74–137 | x 71–74 | x 32–67 | the label, the colon, the value |

All 6 settings shown were out of order before, 0 after. The line still starts at the same left
edge (x 32).

Fix: `apps/web/src/app/[locale]/(app)/settings/page.tsx` — the label and the value now go through
`spaced()` from `@/lib/pieces` (UX-22's helper with a space between the pieces).

## Why no new lint rule

A rule against a hand-typed colon, dash or bracket would flag hundreds of ordinary uses to catch
a shape that occurs once. The dot is different: it is used ONLY to join pieces, which is why
UX-22 could forbid it.

## Checks

| Check | Result |
|---|---|
| Settings' three tabs, the three sweeps (lines of several pieces · single pieces · dot lines) | 0 out of order in each |
| Phone width with a company picked | 0px sideways overflow |
| Lint, typecheck, build (web) | clean |

The full 23-screen sweeps were not repeated: one line in one file changed, and Settings — the only
screen that renders it — was re-swept.

## Limits

- Dialogs, menus and toasts are not open during a sweep; for other separators they rest on the
  code reading above, not on glyph positions.
- Swept as Administrator. The client manager's and the employee's own screens were covered by the
  code reading only.
- The English form of the fixed line was not looked at on screen; in English `spaced()` is a
  plain join (unit-tested), which gives the same text as before.
- Chrome only.
