# UX-23 — Shortened Arabic text hides its beginning — Evidence

- Date: 2026-10-11
- Status: **done**
- Card approved ("approved"). No API change, no component change.

## What was wrong

A line too long for its space is cut and ends in "…". The layout runs left to right in both
languages (ADR-012), so the cut is made at the right-hand edge — and an Arabic line BEGINS at the
right. Its first words were what disappeared.

One line, measured at 375px on the Work queue, in a 64px-wide space:

| «مسؤول علاقات حكومية» | مسؤول (first) | علاقات | حكومية (last) |
|---|---|---|---|
| Before | hidden | shown | shown |
| After | shown | shown | hidden |

## Measured first

A script finds every element that can be cut with "…", checks whether it IS cut, and whether its
first character lies inside its box. 23 screens, Arabic view, Administrator.

| | 375px | 1100px |
|---|---|---|
| Lines that can be shortened | 736 | 772 |
| Actually shortened | 111 | 115 |
| … with the beginning hidden — **before** | **71** | **76** |
| … with the beginning hidden — **after** | **0** | **0** |
| Lines NOT shortened that moved | 0 | 0 |

Not a phone-only fault: People had all 44 shortened lines hiding their beginning at both widths;
the Work queue 19.

## The fix

`apps/web/src/app/globals.css`, on the one class the app uses to shorten text:

```css
.truncate {
  unicode-bidi: plaintext;
  text-align: left;
}
```

- `unicode-bidi: plaintext` — the line takes its direction from its own text, so it is clipped
  at ITS end: an Arabic line keeps its right, an English one its left.
- `text-align: left` — on its own, the first line would also right-align every Arabic line
  ("start" would follow the text). This pins the line to the layout's side. If ADR-012 is ever
  reversed it becomes `right`; the comment in the stylesheet says so.
- Outside any `@layer`, so it outranks `text-start` on the same element (some buttons carry it to
  undo their centring).

### What was tried, in a scratch page, before choosing

| CSS on the shortened line | Arabic | English | Short Arabic line (not cut) |
|---|---|---|---|
| Nothing (today) | **start hidden** | start shown | left |
| `direction: rtl; text-align: left` | start shown | **start hidden** | left |
| `unicode-bidi: plaintext; text-align: match-parent` | start shown | start shown | **pushed to the right** |
| `unicode-bidi: plaintext; text-align: left` | start shown | start shown | left |

A line built by `dots()` (UX-22) — an English name first, then Arabic pieces — also keeps its
start: it opens with a right-to-left mark, which is what the test reads.

## How it was verified against the real stylesheet

First the two declarations were injected into each screen in the browser, before anything was
committed (the "after" column of the prototype run: 0 and 0). Then the rule went into the
stylesheet and the sweep was run the other way round: measure the real page, switch the rule OFF
in the browser, measure again.

| 23 screens | 375px | 1100px |
|---|---|---|
| Beginnings hidden, real stylesheet | 0 | 0 |
| Beginnings hidden, rule switched off | 71 | 76 |
| Lines not shortened whose position differs between the two | 0 | 0 |

The second row is the red proof: without the rule the fault is back, on the same screens, in the
same numbers as the first measurement.

The rule is in the production stylesheet too (`next build`: present in the emitted CSS).

## Not checked

- **Only Chrome.** `unicode-bidi: plaintext` is standard and supported by Safari and Firefox, but
  I could not measure them here.
- **Arabic text shortened inside the ENGLISH view** did not occur on the screens swept (the Arabic
  names under English ones were not cut), so that case rests on the scratch-page test.
- **Text shortened by other means** than this class (a clamp over several lines, for instance)
  is not covered. One multi-line clamp exists in the web app; I found none cut on the swept
  screens.
- The API suite was not re-run: no API file changed.
