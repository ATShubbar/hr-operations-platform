# UX-14 — `GET /requests?status=` actually filters — Evidence

- Date: 2026-07-25
- Task card: `BACKLOG.md` → UX-14
- Status: done
- Commit: `UX-14: make the requests status filter actually filter`
- Found by: UX-13, while re-verifying the labelled filters.

## The defect

`requestQuerySchema` has declared `status` since REQ-02. The controller parsed it and kept
only `clientId`, and the service could not have accepted it anyway:

```ts
const q = requestQuerySchema.safeParse(query);
const clientId = q.success ? q.data.clientId : undefined;   // status parsed, then dropped
const rows = await this.requests.list(clientId);            // list(clientId?: string)
```

Measured before the fix, against seeded data:

```
GET /api/requests              → 9   { open: 4, in_progress: 2, resolved: 1, closed: 1, cancelled: 1 }
GET /api/requests?status=open  → 9   ← should be 4
```

An accepted-and-ignored parameter is worse than a rejected one: the screen showed the full
list under a filter that claimed to narrow it. Behind the old Apply button you pressed a
button and watched nothing happen, which reads as "no matching records"; UX-13's
filter-on-change made the non-response obvious.

## The fix

Filters move into an object, matching the shape Tasks already used:

```ts
list(filters?: { clientId?: string; status?: Prisma.RequestWhereInput['status'] })
listForClient(clientId: string, filters?: { status?: ... })
```

The controller parses **once** and feeds both paths.

**`clientId` is deliberately not a filter on the rep path.** RLS decides whose rows exist;
accepting a `clientId` there would read as though the caller could choose. Asserted: a rep
passing another client's id still gets only their own rows.

Also updated `listByClient` (unused, kept working) and the one service-level test call site.

## The test, proven red before green

Two assertions in `requests-api.e2e-spec.ts`. The load-bearing ones are negative — a test
that only checks "every returned row has status X" passes against a filter that does
nothing, whenever the fixture happens to be uniform. So it asserts the excluded row is
**absent** and the filtered count is **smaller**:

```ts
expect(openRows.some((r) => r.id === reqB)).toBe(false);   // moved to in_progress
expect(openRows.length).toBeLessThan(all.body.requests.length);
```

Run against the **unfixed** source (`git stash` of `modules/requests` only):

```
× Requests API (REQ-02, e2e) > staff filter by status, and it actually narrows
  → expected false to be true
```

Stated honestly: the second test (the client-rep path) **passes either way** on this
fixture, because rep A's own requests are all open. It is a guard against the rep path
regressing, not a red-green proof; the spoof assertion in it is the part that carries
weight.

With the fix: **API suite 352/352** (350 + 2).

## Verified in the browser

Every status, against the true counts:

| status | rows in DB | `?status=` returns |
|---|---|---|
| open | 4 | 4 |
| in_progress | 2 | 2 |
| resolved | 1 | 1 |
| closed | 1 | 1 |
| cancelled | 1 | 1 |

Composes with the client filter: `?status=open&clientId=1111…` → 2 rows, all open and all
client A.

Through the UI — clicking the "Status" label, picking Open:

```
Showing 1–9 of 9   →   Showing 1–4 of 4   (only "Open" in the status column)
Clear filters      →   Showing 1–9 of 9
```
