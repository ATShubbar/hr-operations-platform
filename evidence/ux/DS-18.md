## What changed

### API

| File | Change |
|---|---|
| `@hr/contracts` `vacancy.ts` | New `vacancyPipelineSchema` (`applied`, `screening`, `interview`, `offer`, `hired`, all integers). `vacancyResponseSchema.pipeline` is **required** on every vacancy response. Exported from the index |
| `vacancies.service.ts` | `pipelines(vacancyIds)`: one `groupBy` over `rec_candidates`, **by the vacancy ids given**, never by client. Rejected and withdrawn are not stages on the board and are not counted. Every id gets a full zeroed entry |
| `vacancies.controller.ts` | Every response (list, get, create, update, status, delete) goes through `respond(rows)`. The ids are the rows this request already read on its own path |

**Why this cannot widen a client's reach:**
- A client manager's vacancy rows come from the RLS-scoped read (`listForClient` / `findForClient`), exactly as before.
- Only those ids are counted.
- `app_client` still has **no grant on `rec_candidates`**. The count runs on the staff connection over ids the caller could already see, and returns integers.

**`test/recruitment-vacancy-pipeline.e2e-spec.ts` (new, 5 cases)**, against a fixture of 2 applied · 1 interview · 1 hired · 1 rejected · 1 withdrawn on A's role, and 3 at offer on B's:
1. A's manager gets `{applied: 2, screening: 0, interview: 1, offer: 0, hired: 1}`; an empty role reads all zeros.
2. The pipeline keys are exactly the five stages, all numbers.
3. **Nothing about a candidate reaches the client.** The raw response bodies contain no seeded candidate name or email and no candidate field names, and `/candidates` stays 403.
4. B's vacancy is absent from A's list and 404 by id; B sees only their own, with `offer: 3`.
5. Staff get the same counts, including on a write response (PATCH).

**Proven red first:** before the change, cases 1, 2, 4 and 5 failed (`expected undefined to deeply equal {…}`). Case 3 passed. It is a regression guard, not a red-green proof: nothing leaked before either.

## Found and fixed: client managers could not raise a request

On `/requests`, **New request** opened for a client manager, but **Create never enabled**. The dialog's company picker reads `/clients`, which client managers cannot read, so there was never a company to choose. Yet the API takes their company from the session and ignores any body `clientId`.

For a client rep the dialog now hides the picker and sends no `clientId`. Measured on `/requests`: no company field, Create disabled when empty, enabled once a title is typed.
