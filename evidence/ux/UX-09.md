# UX-09 — the raw-value leak and the workflow control — Evidence

- Date: 2026-07-25
- Task card: `BACKLOG.md` → UX-09
- Status: done

## Half 1 — the raw-value leak

Base UI's `Select.Value` renders the **raw value** when it has no render function.
Measured live on `/ar/employees`, default locale, on the primary entity's create
form:

| Field | Before | After |
|---|---|---|
| نوع العقد (contract type) | **`unlimited`** | `غير محدد` |
| حالة التوظيف (employment status) | **`active`** | `نشط` |

The options in the dropdown were correctly Arabic the whole time; only the
trigger — the thing you look at when the menu is closed — showed the database's
vocabulary.

Nine sites fixed. The highest-leverage was the **shared `SelectField`** on the
employee detail page: it already received a `labelFor` function and simply was
not using it for the trigger, so every govdata and salary edit dialog leaked.

### The lint rule earned its place immediately

`hr/no-bare-select-value` — in the same spirit as the existing
`rtl-safe-classes` and `no-brand-in-status`. A leak that shows an enum key to a
user should fail CI, not depend on someone noticing in review.

On its first run it caught **two sites I had missed by reading**, one of them
worse than anything on my list: the client picker in the employees create dialog,
which rendered a raw **UUID** once a client was selected.

Proven both ways:

```
deliberate violation reintroduced → 1 error   (hr/no-bare-select-value)
restored                          → lint clean
```

### The calendar, filed during UX-05

`/ar/calendar` rendered `· ${it.status}` raw, and — like Today before UX-04 — used
the GRO process **type** as the item title. `/calendar/view` merges four domains
and returns raw enums, so this was the second screen with the same bug, which is
what justified extracting `lib/view-item-labels.ts` rather than copying Today's
helpers. Today now uses it too, so the mapping exists once.

After: `طلب … الاستحقاق · قيد المعالجة`, and a scan for raw enum tokens on the
agenda returns **zero**.

## Half 2 — one workflow control

Four screens advance an item through a status workflow, and each had built its
own affordance: vacancies a Select in the row, candidates a Select on a board
card, requests and GRO a button opening a dialog. Same decision, four shapes.

`components/ui/status-action.tsx` owns exactly the shared part — *given the
current status, offer the legal next ones, translated* — and deliberately not
what happens afterwards.

| Screen | Before | After |
|---|---|---|
| Vacancies | inline Select | `StatusAction` |
| Candidates | inline Select on card | `StatusAction` (keeps "Hire" for `hired`) |
| Requests | button → dialog containing only a status Select | `StatusAction`, applied from the row |
| GRO | button → dialog with status Select **+ conditional expiry** | `StatusAction`; dialog opens **only** for the transition that needs the extra field |

**Requests lost its dialog because the dialog held nothing.** It showed the title
and current status — both already in the row — and a Select. Three clicks to
deliver one choice.

**GRO kept its dialog because it earns it.** Completing an expiry-bearing process
writes the resulting expiry back to the employee's govdata (GRO-03). Now the row
picks the status and the dialog asks for *only* the expiry:

```
summary line : جوزيف سانتوس · تجديد رخصة عمل → مكتملة
fields asked : الانتهاء الناتج
re-asks status: false
```

### Verified per role, driving it as a user

- **hr_officer / Requests:** menu offered exactly `قيد المعالجة`, `ملغى` for an
  open request; choosing applied it in one click and the row moved
  `مفتوح → قيد المعالجة`. Terminal rows (`مغلق`, `ملغى`) show "no further steps"
  rather than an empty cell.
- **gro_officer / GRO:** a `submitted` process offered approve/reject/cancel and
  no "complete" — the workflow routes through `approved`, and the menu reflects
  that. Completing an approved work-permit renewal opened the one-field dialog,
  saved, and the row showed `مكتملة` with the resulting expiry rendered
  dual-calendar.
- **recruiter / Vacancies + Candidates:** menus on live rows, "no further steps"
  on `ملغى`/`مغلق`, `نقل إلى…` on board cards.

### One consistency fix the unification exposed

Vacancies and GRO passed their own `terminal` string, which was `—`. Requests and
Candidates had no such key. So the same control was saying two different things
about the same state. They now all fall through to one shared
`states.terminal` — "لا خطوات إضافية" — which says *why* there is no menu instead
of drawing a dash.

## Dev-data hygiene

Exercising real transitions mutated seeded rows, so the seed was re-run. One
residue needed a manual clear: the seed's GRO update payload does not include
`resultingExpiry`, so the value I set through the UI survived the reseed. Cleared,
and the table now matches the seeded shape exactly.
