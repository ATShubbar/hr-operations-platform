# UX-20 — Arabic sentences that lay out in the wrong order — Evidence

- Date: 2026-10-11
- Status: **done**
- Card approved ("approved"). No API change.

## What was wrong

The layout runs left to right in both languages (ADR-012). An Arabic message reads in order
there only while it is one right-to-left run. Three things broke that. Each was measured in the
browser before any code was written (the x position of each piece; an Arabic line starts at the
RIGHT):

| Fault | Example | Measured | 
|---|---|---|
| Ends in punctuation | «تعذّر الحفظ. حاول مرة أخرى.» | first word at x 133–158, the final stop at x 158–162 — drawn BEFORE the sentence |
| An English name inside | «أصبح Huda Al-Qahtani مسؤولًا عن هذا الملف.» | first word x 0–33, name x 37–154, the rest x 235–273 — three pieces laid out left to right |
| Opens with an English name | «Huda Al-Qahtani يملك هذا الملف» | name at x 0–117, the far (wrong) end |

What fixes each, measured the same way:

| Tried | Stop at the end | Name inside | Name in front |
|---|---|---|---|
| A right-to-left mark at the end | fixed (stop at x 0–4) | no change | — |
| A mark at both ends | fixed | **no change** | **no change** |
| The name sealed in an isolate, plus marks at the ends | fixed | fixed | fixed |
| The whole message in one right-to-left isolate | fixed | fixed | fixed — **but** see below |

The last row was rejected. A line built from several pieces — "target date · Hijri date" — reads
correctly today (target at x 259, Hijri at x 93). With the first piece wrapped whole, the two
swap (target x 101, Hijri x 274). The chosen rule leaves such lines alone.

## The rule, and where it lives

`packages/text/src/bidi.ts` — `rtlSafeMessage` / `rtlSafeMessages`, exported from `@hr/text`:

- every slot (`{name}`, `{n, number}`, `{d, date}`) and every English word or phrase is sealed
  in an isolate — inside plural and select branches too;
- a right-to-left mark is added at an end that is not an Arabic letter;
- left exactly as it came: a message with no Arabic letter, one that already holds a directional
  control (so applying the rule twice changes nothing), and one whose braces do not balance.

Applied in ONE place, `apps/web/src/i18n/request.ts`, when the Arabic messages are loaded, once
per loaded file. English is never passed through it.

`apps/web/messages/ar.json` is plain text again: UX-18's 201 hand-placed marks were removed.
After removal the file differs from the pre-UX-18 file only by messages later cards changed.

Cost, measured: 900 marks and 367 sealed pieces over the file; the message payload grows by
4.9 KB (0.5 KB compressed); one pass takes 1.7 ms.

## A side effect found by measuring, and fixed

The People summary passed its range as ONE value ("8–14"). Sealed as a single piece, a range is
drawn left to right — 8 on the left — while the filter beside it, a fixed message, runs right to
left. The message now takes two slots (`{from}–{to}`), and reads as in the table above. It was
the only message with a range in one slot.

## Corrections to UX-18

- UX-18's check said a leading placeholder "may hold a number, a date or a Latin name" and that
  the mark handles it. Measured: the mark fixes a leading NUMBER only. A leading English name
  stayed at the wrong end until this card.
- UX-18's 201 marks and its check are replaced by the rule and the check above. What UX-18
  delivered — a leading number at the right-hand end — is unchanged, and is now a tested case.

## Found, not fixed

1. **Arabic dates standing alone are out of order** → UX-21. Measured on People: «3 أكتوبر 2026»
   is drawn day x 817, year x 829, month x 865 — read from the right, "October 2026 3". Dates are
   formatted in code, in 97 places across 40 files, so this is its own card.
2. **Lines assembled from data** (name · company · department; "Procedure #id") → UX-22.
3. **Screen readers** were not tested. The marks are also inside labels and input hints; screen
   readers normally ignore them.
