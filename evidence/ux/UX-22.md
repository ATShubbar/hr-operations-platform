# UX-22 — Lines assembled from several pieces read out of order — Evidence

- Date: 2026-10-11
- Status: **done**
- Card approved ("approved"). Owner decision: in the Arabic view an all-English line also runs
  from the right ("From the right, like the rest"). No API change.

## What was wrong

Many lines are built in code by joining pieces with a dot: job · company · department. In the
Arabic view, when one piece is English the browser places it at the wrong end and the Arabic
pieces around it swap. «محاسب · شركة الألف التجارية · Finance» was drawn company, then job, then
"Finance" at the right — read from the right: Finance, job, company.

## Measured first

A second script, because the UX-20 one judged single pieces of text and so missed lines built
from several elements. It walks each line that contains the separator and checks, by glyph
position, that every piece starts to the LEFT of the piece before it.

| 23 screens, Arabic, Administrator, 1100px | Before | After |
|---|---|---|
| Dot-separated lines | 226 | 226 |
| … out of order | **97** | **0** |

Every screen holds the same number of lines before and after. The worst before: Audit trail 46
of 48, Mobilisation tab 12 of 20, a request 10 of 11, Hiring 7 of 21, Work queue 6 of 30.

The UX-20 sweep, re-run as a regression check: pieces out of order 28 → 2 (the two "People &
Gro" lines that script miscounts); sentences with the stop at the wrong end still 0; dates still
0.

## The fix

- `@hr/text` → `rtlSafeJoin(pieces, { rtl, separator })`:
  - empty pieces are dropped with their separator;
  - right to left: every piece is sealed in an isolate and a mark at each end makes the pieces
    run from the right, first piece first, whatever language each is in;
  - left to right (English): a plain join, no invisible character;
  - one piece left is returned as it is.
- `apps/web/src/lib/pieces.ts` (new): `dots(locale, …pieces)` and, with a space instead of a dot,
  `spaced(locale, …pieces)` — used for the Audit trail's "Procedure #e470adc9".
- `apps/web/src/components/ui/dot-line.tsx` (new): `<DotLine>` for a line whose pieces are not
  all text (a reference in its own element, a status). Same rule, with `<bdi>` per piece.
- **The sweep:** every hand-joined line in the web app — 92 places in 47 files — now goes through
  one of those: 85 `dots()` calls, 2 `<DotLine>`, 1 `spaced()`. 52 were converted by pattern, the
  rest by hand. Six components gained the current language to pass in.
- **A gap in UX-20's rule, found by this sweep and closed.** Three Arabic-file messages are made
  only of slots joined by a dot — `{name} · {role}`, `{resource} · {action}`. They hold no Arabic
  letter of their own, so the message rule skipped them, and "Turki Al-Harbi · مسؤول علاقات
  حكومية" stayed out of order on the History tab (the one line left after the code sweep). The
  rule now treats a slots-and-dot message in the Arabic file as a line. A slots-only message
  WITHOUT the dot — `{count} / {total}`, `{from}–{to}` — is still left alone. The whole-file
  check now reports 845 messages marked (842 before), wording of none changed.

## The lint rule

`hr/no-hand-joined-line` (`packages/config/eslint-plugin-hr.mjs`), on for the web app: the
separator may not be typed in a string, a template or JSX text anywhere except the helper and
the component.

| Proof | Result |
|---|---|
| `['a', 'b'].join(' · ')` added to a page | error |
| `` `${a} · ${b}` `` | error |
| `{a} · {b}` in the page's markup | error |
| Restored | clean |
| One exemption, commented: the avatar's placeholder glyph for a missing name | clean |

Running the rule for the first time listed all 92 places — that is how the sweep was driven.

## Not checked, and found

- **The API suite was not re-run locally**: no API file changed; CI runs it.
- **Lines joined with other separators** (a dash, a slash, brackets) were not measured.
- **Screen readers** were not tested; the invisible characters are in labels too.
- **UX-23 — shortened Arabic text hides its START.** Where a line is too long for its space and
  is cut with "…", the first word is what disappears. Measured at 375px on the Work queue: 19 of
  25 shortened Arabic lines have lost their first character («مسؤول علاقات حكومية» shows only its
  end). A different mechanism from this card; not fixed.
