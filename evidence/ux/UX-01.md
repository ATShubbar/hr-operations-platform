- Date: 2026-07-25
- Task card: `BACKLOG.md` → UX-01 (UI/UX epic; [design proposal](https://claude.ai/code/artifact/728af94a-5bab-485c-89e6-76aef6a8a39c))
- Status: done
- Commit: `UX-01: semantic status tokens separate from the brand + surface layering`

## Why this card exists

The theme defined `--primary` (a gold at hue 92) and `--destructive`, and **no
`--warning`, `--success`, `--info` or `--neutral` token at all**. So the brand
accent and the warning colour were the same hue by construction: anything tinted
amber read as *brand*, not as *caution*. In a product whose most important state
is "this document expires soon", the most important warning had the weakest,
most-diluted colour available.

Separately, `--background` and `--card` were both `oklch(1 0 0)` — the same pure
white — so every card and table was distinguished only by a hairline. That is the
mechanical reason the app read as flat rather than designed.

## What shipped

**A third token tier**, structurally separate from the brand. Three roles per tone:

| Role | Purpose |
|---|---|
| `--status-<tone>` | the tone itself — text, dots, icons, and any **unlabelled** fill such as a bar |
| `--status-<tone>-surface` | the tint behind a labelled pill |
| `--status-<tone>-line` | a decorative hairline, explicitly **not** load-bearing |

Tones: `critical · warning · ok · info · neutral`. **Warning is orange, not gold** —
redder and darker than `--primary`, so it is distinguishable from the brand side
by side and survives the red-green confusion axis that makes amber the weakest
status hue.

**Surface layering:** `--background` → `oklch(0.975 0.003 95)`, `--card` stays at
`1.0`. The neutral is biased very slightly warm (hue 95) toward the gold accent —
a chosen neutral rather than an inherited grey.

### Three things the measurement changed

Worth recording, because each corrected an assumption in the task card:

1. **Dots use the tone colour, not the line colour.** I had planned "borders and
   dots ≥3:1". The hairlines measure ~1.5:1 against the page — but 3:1 does **not
   apply** to them: WCAG 1.4.11 exempts the boundary of a control whose meaning is
   carried by its own visible text. So the border is explicitly decorative, and a
   status **dot** (which *is* a graphical object carrying meaning) draws from
   `--status-<tone>` at 6.0–8.9:1. One fewer token role to reason about, and the
   requirement lands where it actually belongs.

2. **An unlabelled fill must use the tone, not the surface tint.** The tints
   measure 1.02–1.06:1 against the page — a bar drawn in `--status-critical-surface`
   would be effectively invisible. Recorded in the token comments so UX-04's
   bucket bars don't reach for the tint.

3. **A monotonic greyscale ramp across five hues is incompatible with holding all
   five at 4.5:1 on a light tint.** Measured luminances: critical 0.069 → info
   0.100 → warning 0.104 → ok 0.121 → neutral 0.125. Critical is clearly darkest
   (which is the one that matters), but the middle three are close. Pushing them
   apart means lightening the text, which breaks 4.5:1. So **non-colour redundancy
   comes from the label and icon** — which is what WCAG 1.4.1 actually requires —
   and ordered/quantitative data uses the existing `--chart-1..5` lightness ramp,
   which is inherently colour-blind-safe. Stated plainly rather than claiming a
   ramp that doesn't hold.

## The guardrail

New lint rule **`hr/no-brand-in-status`** (`packages/config/eslint-plugin-hr.mjs`),
`error` in `apps/web/eslint.config.mjs`. It flags brand utilities
(`bg-primary`, `text-primary`, `border-brand`, …) and raw `var(--primary)` /
`--brand` references inside files whose path contains `status`.

Verified with a temporary probe (since deleted) — it caught all three violations
and passed the legal tier:

```
12:23  error  'bg-primary' puts the brand accent on a status surface — use the --status-* tier …
12:23  error  'text-primary-foreground' puts the brand accent on a status surface …
13:29  error  'var(--primary)' references the brand token from a status file …
✖ 3 problems (3 errors, 0 warnings)
```

**Why it's scoped to `status` files and not `badge` files** — a deliberate line,
not a loophole. `Badge` is arbitrary metadata whose colour is decorative (a
brand-filled "New" badge is legitimate); `StatusPill` communicates workflow state
and its colour is semantic. Those are different components with different rules
and must not be merged. The rule therefore has nothing to bite on until UX-02
lands `StatusPill` — the fence goes up before the field is planted.

## Browser verification (live, both locales)

| Check | Result |
|---|---|
| All five tone tokens resolve on `:root` | ✅ `critical oklch(0.43 0.17 25)` … `neutral oklch(0.5 0.012 285)` |
| **Tailwind v4 `@theme` wiring produces real utilities** | ✅ `bg-status-critical-surface` → `oklch(0.96 0.022 25)`, `text-status-critical` → `oklch(0.43 0.17 25)`, `border-status-critical-line` → `oklch(0.84 0.07 25)` |
| Surface layering paints | ✅ body `oklch(0.975 0.003 95)`, card `oklch(1 0 0)` — tables now read as raised surfaces |
| No regression, en (LTR) | ✅ `/en/employees` |
| No regression, **ar (RTL)** | ✅ `/ar/gro` — filters, table, dual-calendar column all correct |

Note on utility generation: Tailwind v4 only emits a utility when it appears in
scanned source, so these classes materialise as consumers adopt them. The probe
above is what proved the `@theme` wiring is correct rather than assuming it.

## Dark mode: deliberately unreachable

Owner decision — not shipping. The `.dark` block stays in `globals.css` because
it is shadcn preset output and deleting it would drift from the preset, but it now
carries a header stating it is **deliberately unreachable**: no toggle, no
provider, nothing adds the class. Recorded so a future session doesn't find it and
mistake a declined feature for unfinished work.
