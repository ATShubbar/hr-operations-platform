## A correction first

UX-13's card, and the UX-12 evidence before it, said `/employees` is the only list
controller that accepts `clientId`. **That is wrong.** Documents, requests, tasks,
vacancies and GRO all accept it — through `@Query() query: unknown` plus a zod schema,
which a grep for `@Query('clientId')` does not find. All six already filtered
server-side; this card is presentation only. Corrected in `employees/page.tsx` and in
CLAUDE.md.

## What actually differed per screen

The card assumed five Apply buttons. There were two.

| Screen | Before |
|---|---|
| requests, tasks | `<form>` + **Apply** + Clear, above the table |
| vacancies, GRO | labelled row above the table, already filtering on change |
| documents | `<form>` + **Apply** + Clear, three filters incl. a date |

All six now render their filters in `DataTable`'s `filters` slot, beside the search.

## Measured — filtering, one request per action

```
/en/requests    9  → 5   /api/requests?clientId=1111…       clear → /api/requests        → 9
/en/tasks       4  → 1   /api/tasks?status=open             clear → /api/tasks           → 4
/en/vacancies   9  → 3   /api/vacancies?clientId=1111…      clear → /api/vacancies       → 9
/en/gro        17  → 8   /api/gro-processes?clientId=1111…  clear → /api/gro-processes   → 17
```

`Clear filters` was **absent before filtering and present after**, on all four.

Tasks shows 4, not 10, because `hr_officer` has no `task.read-all` and the list is
own-scoped — the risk flagged in the card. The filter narrows within that scope, which is
correct: it must not become a way to see other people's tasks.

## Documents — the one non-Select filter, and the one that had to compose

Three controls that must **stack**, not replace each other:

```
start                                        20 docs   /api/documents
set date 2026-08-15                        →  8 docs   ?expiringBefore=2026-08-15
then category Iqama                        →  6 docs   ?category=iqama&expiringBefore=2026-08-15
Clear filters                              → 20 docs   /api/documents
                                             date input value after clear: ""
```

Exactly three requests, one per action. The date field fires on `change`, not `input`: an
`<input type="date">` reports `''` until all three segments are filled, so committing a
date produces one request rather than one per keystroke. Verified — no spurious unfiltered
fetch.

The handler is a single `applyFilters(patch)` that merges over current state, which is
what makes the composition above work; three independent setters would have raced each
other into a stale `load()`.

## Two component changes, made once instead of six times

**Clear moved into the toolbar** (`DataTable`), rendered only while `narrowed`. It
previously existed *only* in the no-results state — which is when you need it least, since
you can see there is nothing there. Resetting three active filters one Select at a time
was the case the Apply-button forms handled and the inline shape had dropped.

**The search input is now 32px.** `h-9` passed to a `SelectTrigger` is dead code:
the component carries `data-[size=default]:h-8`, an attribute variant that outranks a
plain utility and that tailwind-merge will not strip. Measured — search 36px beside
filters at 32px in the same row. Aligned the search on the component's own default rather
than fighting the variant, and deleted the dead class from all six screens (including the
Employees filter shipped in UX-12, where it had never applied either).

Same failure family as UX-11's `not-sr-only` padding: a variant selector silently beating
a utility, invisible until measured.

## Arabic

```
one row, 0px overflow, search at the START (right) edge of the row on every screen
aria-labels resolve: العميل · الحالة · النوع · تنتهي قبل · تصفية حسب الشركة
```

At 375px the controls wrap to one per row (documents: 4 rows), all inside the viewport,
**0px page overflow**.

## The trade-off, stated

Sighted users lose the word "Client" above the control; it survives as `aria-label`, so
screen-reader users lose nothing. On a three-filter screen like documents this is the
thing to look at first if the compact row reads as ambiguous — the Select shows "All"
until narrowed, which carries less than a label did.
