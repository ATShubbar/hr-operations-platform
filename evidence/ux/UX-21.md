# UX-21 — Arabic dates read in the wrong order — Evidence

- Date: 2026-10-11
- Status: **done**
- Card approved ("approved"). No API change.

## What was wrong

Under the left-to-right layout (ADR-012) an Arabic date standing on its own opens with a
number, and a leading number is placed at the LEFT. Measured on People before the change:

| «3 أكتوبر 2026» | day | month | year | Read from the right |
|---|---|---|---|---|
| Before | x 817 | x 865 | x 829 | "October 2026 3" |
| After | x 883 | x 853 | x 817 | "3 October 2026" |

Hijri dates and times had the same fault. Dates are made in code, so UX-20's rule for messages
never saw them.

## The fix

- `@hr/text` → `rtlSafeValue(value)`: a right-to-left mark in front of a value that has Arabic
  in it and does not open with an Arabic letter. Nothing behind — a number that follows Arabic
  text already sits inside its run. An English value comes back untouched.
- `apps/web/src/lib/dates.ts` (new) — the one place the web app formats a date or a time:
  - `dateFormat(locales, options)` — takes exactly what the browser's formatter takes, so no
    date changes its wording;
  - `hijriDate(date, locale)`, `gregorianDate(date, locale)`.
- A sweep: **96 calls in 44 files** now go through it (67 direct uses of the browser's formatter,
  28 of the Hijri formatter, 1 of the Gregorian one).
- One call is deliberately NOT swept: `riyadhToday()` in `lib/leave.ts` builds a day for
  arithmetic, not for the screen. It keeps the browser's formatter, with a comment.
- The shared `@hr/dates` package is unchanged: the API uses it too (the health check), and a
  mark must not enter API output.

## The lint rule

`apps/web/eslint.config.mjs`: in the web app, outside `src/lib/dates.ts`, it is an error to
construct the browser's date formatter or to import `formatHijri` / `formatGregorian`.

| Proof | Result |
|---|---|

| The Hijri formatter imported directly | error — "'formatHijri' import from '@hr/dates' is restricted…" |
| Restored | clean |
| `lib/dates.ts` and `lib/leave.ts` | clean |

## Not checked, and found

- **A time on one line was not measured on screen.** The only Arabic time found on the swept
  screens is in the Audit trail's time column, which is 44px wide: «12:48 م» wraps there, the
  letter under the digits. The wrap is not new — the mark has no width — and is left as it is.
  The time case is covered by the function's tests and by the sweep counting no piece out of
  order.
- **The API suite was not re-run locally.** No API file changed (the API consumes `@hr/text`,
  which only gained an export); typecheck and build pass, and CI runs the suite.
- Lines assembled from data → UX-22, unchanged.
