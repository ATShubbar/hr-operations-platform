## What shipped

`components/ui/load-state.tsx` — two components, because the two cases want
opposite things:

- **`LoadError`** — the request FAILED, so it offers a retry that re-runs the
  loader in place.
- **`NoAccess`** — the request was REFUSED (403). Retrying a permission denial
  just fails again, so it has **no retry**; it names the missing capability
  instead, because the user's real next step is to ask someone for it.

Plus skeletons on the seven non-list screens (lists already get theirs inside
`DataTable`), and `EmptyState` for the non-list empties (calendar agenda,
candidate lanes, expiry buckets).

### `LoadError` decides by whether content is on screen

Several screens funnel a failed **load** and a failed **row action** into the
same `error` state — Documents' download is the clearest case. Replacing the
whole table when a download fails would destroy the list the user is working in.
So: **content present → a banner above it; nothing to show → it takes the
region.** Verified both branches (below).

## The defect this card existed to find

**A dead API logged you out of the interface.**

`SessionProvider` redirected to `/login` on *any* rejection from `/auth/me` —
including a network error or a 500. So every screen's careful error-with-retry
state was unreachable when it mattered most: the guard bounced first and dumped
you on a sign-in form that also failed, with a perfectly valid session cookie
still in the jar.

Measured, by stopping the API mid-session:

| | Before | After |
|---|---|---|
| Navigate with API down | → `/ar/login` | stays on `/ar/documents`, error + retry |

Now only a real 401/403 goes to sign-in; anything else keeps you in the app. The
guard's blank `return null` while resolving also became a skeleton.

## Two defects found while verifying

**1. A screen reader would have announced "calendar.loading".** The skeleton
label used each screen's own `t('loading')`, and `calendar` and `candidates` have
no such key — next-intl returns the key path, so the loading announcement was
literally `calendar.loading`. Every skeleton label now points at one shared
`states.loading`, which cannot rot per namespace. Re-verified: announces
`جارٍ التحميل…`.

**2. Settings swallowed its own error.** It returns early when `!me`, rendering
`{error || t('loading')}` — so a failed load showed a grey "loading…" *forever*
and the retry I had just added below was unreachable. The early return now
handles error and loading separately.

## One thing I fixed rather than introduced

The 403 copy embeds a Latin permission id in an Arabic sentence, which drags the
sentence's full stop to the wrong side. That is the bidi-isolation bug UX-08 is
scheduled to clean up — but I was *adding a new instance of it*, so the
capability is wrapped in `<bdi>`. Verified present in both locales.

## Scope held

Form and mutation errors stay inline next to their submit button. That is not an
omission: the failure belongs beside the control that caused it, and a
page-level banner loses the field context.

```
before: 34 destructive paragraphs
after : 16 — every one a formError / procError / stError / dialog err,
             plus the login form's own. Zero page-level load errors.
```

Toasts for *successful* mutations were left out — success is not one of this
card's four states, and `Toast` still has no consumers (UX-09).
