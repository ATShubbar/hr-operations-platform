## Why the obvious way was wrong

1. **The repository is public, so the seed's dev password is public.** Seeding an internet-facing UAT with it would let anyone sign in as an administrator.
2. **The seed refused production mode** (UAT runs `NODE_ENV=production`), and that refusal must keep protecting the real production.

## What was built (`b1dd172`)

| Piece | What it does |
|---|---|
| `apps/api/prisma/seed-guard.ts` | Production mode is allowed **only** with `SEED_TARGET=uat` **and** a supplied `SEED_PASSWORD` (at least 16 characters, never the public dev one). Development is unchanged. The real production never gets either. |
| `apps/api/test/seed-guard.e2e-spec.ts` | Red first (module absent), then **4/4**. Both refusals were also shown in a shell and inside the built image, **before any database connection**. |
| Dockerfile target `seed` | The builder workspace the seed needs. Not used by any deploy; CI always names its targets. |
| `apps/api/scripts/uat-smoke.mjs` | The per-role check. It runs through the public web address, exactly as a browser would. **25/25 against the local stack; fails (exit 1) on a wrong password.** |
| `.github/workflows/uat-seed.yml` | **Manual only** (`workflow_dispatch`), keyless (Workload Identity Federation). Jobs `uat-seed` and `uat-smoke`. |
| Service account `uat-seed` | `cloudsql.client` conditioned to `uat-*` instances; accessor on `uat-database-url` + `uat-seed-password` **only**; registry reader. `uat-deployer` may act as it. |
| Secret `uat-seed-password` | **Generated by the owner** in their own terminal (`openssl rand` piped into Secret Manager), `me-central1` only, never displayed. |

## Notes and follow-ups

- **Seeded documents have no files** (SEED-01), so "Download" on seed data fails on UAT exactly as it does locally. The smoke check uses a freshly uploaded file instead.
- **Re-running "Seed UAT" with `seed-and-smoke` resets the sample data AND the seed accounts.** The seed deletes and re-creates every `@seed.hr.local` user (`seed.ts`, `seedUsers`), so the owner's authenticator enrolment is wiped. They would enrol again and should delete the old entry in their authenticator app. Use `smoke-only` just to check.
- The smoke check is the regression test for every future UAT deploy. Run it after anything that touches auth, storage or the worker.
- Found while closing: `notification-email.e2e-spec.ts` flaked in CI (`expected 42 to be 41`). Its worker module drains other specs' leftover jobs from the shared Redis, and the assertion counted every captured email. It now counts only mail that spec could cause (`dc47398`).
