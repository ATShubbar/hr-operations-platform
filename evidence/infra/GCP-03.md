## Access checks

- **No `uat-*` service account holds any project-level role.** The project IAM policy filtered on `uat-` returned nothing.
- **Resource-scoped grants only:**

  | Grantee | Role | On |
  |---|---|---|
  | `uat-run` | `artifactregistry.reader` | repository `peoplegro` |
  | `uat-run` | `storage.objectAdmin` | bucket `peoplegro-uat-documents` |
  | `uat-redis-vm` | `artifactregistry.reader` | repository `dockerhub` |
  | `uat-redis-vm` | `secretmanager.secretAccessor` | secret `uat-redis-password` only |
- `uat-db-migrator-password` has **no** service-account access yet. Wiring comes in GCP-04.

## The Redis VM boots correctly

From the VM's serial console, read-only:

```
startup-script: Status: Downloaded newer image for me-central1-docker.pkg.dev/peoplegro-prod/dockerhub/library/redis:7-alpine
startup-script exit status 0
```

- The password is read from Secret Manager into a **root-only** config file on the VM. It's never in the VM's metadata or on a command line.
- Redis runs with no persistence, and with `noeviction`, which BullMQ requires.
- The first **application** connection (Cloud Run → Direct VPC egress → 10.212.0.2:6379, with the password) is proven in GCP-04.

## Notes and follow-ups

- **Before production:** the default network's `default-allow-ssh` and `default-allow-rdp` rules are open to `0.0.0.0/0`. They're harmless to our IP-less VM, but should be tightened before production. Logged in the runbook.
- **For GCP-04:**
  - The `app_staff` / `app_client` / `app_employee` roles are created by the first migration with **development passwords**. They're rotated immediately after, using the same owner-generated-secret method.
  - `uat-run` gets `cloudsql.client` (conditioned to `uat-*` instances) when the services are wired.
- **This shell's `gcloud`** needs `CLOUDSDK_PYTHON=/opt/homebrew/bin/python3.14`, because macOS's Python 3.9 is unsupported.
