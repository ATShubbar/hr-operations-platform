### Why a separate login role (decided in the card)

Reusing the client-rep connection and switching role mid-transaction (`GRANT app_employee TO
app_client` + `SET LOCAL ROLE`) would save one env var — but Postgres applies a policy `TO
app_employee` to every MEMBER of `app_employee`, so the employee policies would start applying
to client-rep queries. A separate login role has no such interaction and mirrors ADR-001's one
connection per trust level. The warning is now in the module checklist.

## Verification

### Database — `test/rls-employee.e2e-spec.ts`: 14/14

Fixtures created by the spec (owner connection): **me** and a **colleague** at client A, an
**outsider** at client B; documents: 2 mine, 1 colleague's, 1 outsider's, 1 company-level
(`employee_id NULL`).

| Test | Result |
|---|---|
| UNFILTERED `employee.findMany()` as me | `[me]` only |
| colleague / outsider by id | `null`, `null`; `where: { clientId: A }` still `[me]` — filtering by my company doesn't widen to colleagues |
| UNFILTERED `document.findMany()` as me | `mine-1`, `mine-2` — not the colleague's, not the company-level document |
| colleague's own scope | sees only `colleague` — the fence follows the scope, not the company |
| interactive transaction | `{ employees: 1, documents: 2 }` |
| raw `app_employee`, NO scope | 0 employees, 0 documents (not an error, not everything) |
| pooled reuse | 12 scoped transactions, then 12 concurrent unscoped counts → all 0 |
| writes (update own record, insert a document, delete own documents) | all `permission denied` |
| `req_requests`, `cli_clients`, `auth_users`, `aud_entries`, `gro_processes`, `task_tasks` | all `permission denied` |

**Proven to fail when the fence is wrong:** `ALTER POLICY employee_self ON emp_employees
USING (true)` → **5 failed** (exactly the employee-row assertions: unfiltered, by-id,
transaction, unscoped, pooled); restored → 14/14. Both policies re-read from `pg_policy`
after restore:

```
emp_employees|(id = (NULLIF(current_setting('app.employee_id'::text, true), ''::text))::uuid)
doc_documents|(employee_id = (NULLIF(current_setting('app.employee_id'::text, true), ''::text))::uuid)
```

### Isolation harness — 12/12

- **Principal fence:** every registered route outside `public / session / self / employee`
  called as an employee → **403**, all of them (offenders collected and listed on failure).
- **Proven to catch ADR-011's unsafe grant:** temporarily adding `employee.read` to the
  employee role →

  ```
  × every route outside public / session / self / employee REFUSES an employee principal (403)
  +   "GET /employees -> 200",
  +   "GET /employees/:id -> 404",
  ```

  i.e. an employee would have been served the **cross-company employee list**. Reverted;
  `git diff` on `permissions.ts` empty. This is the CI tripwire SS-03 must pass.
- **`employee` class:** registered members = **0**. The loop runs only when it has members
  (`describe.runIf`); until then a single test asserts the set is empty, so the gap is
  visible in the output rather than a silently-passing loop. **It proves nothing yet** —
  SS-03's first route starts it (own record → contains my id; same-company colleague → does
  not; unauthenticated → 401).
- Coverage diff (every live route registered and vice versa) still passes; `POST
  /auth/logout` reclassified to `self` (its unauthenticated → 401 check still runs).
