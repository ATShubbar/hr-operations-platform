## The permission question, settled

ADR-011's original list gave employees `employee.read` / `salary.read` / `govdata.read` /
`document.read` — the names the STAFF list endpoints check, which ignore the principal (SS-01
finding; SS-02 proved it: `GET /employees -> 200`). The employee role now holds **`session.end`
+ `self-service.read`** only, and data reaches employees solely through `/me` — the
`portal.read` pattern. Recorded as **ADR-011 rev. 2**.

### `GET /me`, in order

1. Guard: `self-service.read` (employee role only → staff and client reps 403).
2. Context must be an `employee` principal with an `employeeId` (defence in depth).
3. `EmployeesService.getSelf(session employeeId)` through app_employee — no record → **404**.
4. `flag.employee-self-service` for **the record's** company — off → **403**. Read per
   request, so a transfer takes effect immediately (ADR-011 rev. 1).
5. `employmentStatus === 'terminated'` → **403** (backstop until SS-06).
6. Company name via `ClientsService`, then `toSelfProfileResponse`.

**Proven to bite:** temporarily spreading `clientId` into the self view → **2 failed** (pinned

First run hit SS-01's unique index again (three tests each created an account for the same
record) — fixed by sharing one session. The constraint doing its job, a second time.

### Isolation harness — 14/14

`GET /me` is the first `employee` route, so the class loop now RUNS (the "none registered"
marker disappeared): own record contains the caller's id · **a same-company colleague's
response does not** · unauthenticated 401. The principal fence stays green: no staff or
client-rep route answers an employee.
