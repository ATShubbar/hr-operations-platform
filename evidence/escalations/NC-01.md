- Date: 2026-10-10

- No screen yet. That is NC-03.

## What changed

**Rules** (`@hr/contracts/escalation-rules`, no zod, so the web can import it):

- The three rules, the four stages in rising order, the default thresholds and the fixed list of allowed day values.
- `stageFor(rule, daysLeft, thresholds)`: the highest stage reached, or none. Breach only once the date has passed.
- `STAGE_AUDIENCE`: who is told at each stage. Fixed by the ADR.
- Who owns each kind of document when no officer is named, and which procedures renew which document.
- `thresholdOrderProblem`: a later stage may not start earlier than the one before.

**Engine** (`apps/api/src/modules/escalations/domain/ladder.ts`). A pure function: it is handed the register as plain rows and who is asking, and returns what that person is shown. It reads nothing, so every rule is tested without a database.

**API.** A new delivery module, `escalations`. It imports Auth, Clients, Configuration, Employees, GRO, Requests and Tasks; nothing imports it.

| Route | Permission | Answer |
|---|---|---|
| `GET /escalations` | `escalation.read` (all four staff roles), staff only through `scopeOf` | `today`, the `thresholds` in force, `items` (most urgent first), and `suppressed` (how many expiries are quiet) |

Each item: a stable key, its rule and stage, the date and days left, what it is about, the client, the owner (a name or a role, never an id or an email), and two flags for the viewer: `mine` and `told`.

**Setting.** `escalation.thresholds` (system level). Changed through the existing `PATCH /config/system/…` (`config.write`, Administrator), validated strictly, audited like any setting.

Also: `DependantsService.listForEmployees` (one read for many sponsors), the matrix row "Escalation ladder", and the route in the isolation registry.

## Stated plainly

- **My own API test was flaky and I caught it only in the full run.** Two items at the same stage with the same days left are ordered by their key, and the keys in that test contain generated ids, so the expected order was right about half the time. It passed alone and failed in the suite. The order of stages and days is still asserted as written; only ties are now settled by sorting. Ran four more times alone and once in the full suite, all green.
- **Nine of the eighteen sample expiries are quiet.** That is a lot. Part of it is real (the seed has renewals in progress), and part is left over on my machine: earlier test runs auto-opened renewal procedures that the seed does not remove. UAT will show fewer. NC-06 will set the sample data so each stage has something in it.
- **The sample ladder is mostly Breach** (21 of 32) because the seed's procedures and tasks were written with many past-due dates. Again NC-06.
- **"Today" is the system timezone's date**, and the API test counts its days the same way (the BILL-05 lesson).
- **Client managers and employees get 403** until NC-05. A test proves that holding the permission would not be enough.
- **The four points in ADR-021 rev. 1** (one obligation reported once; Saudi nationals; role-owned items; the quiet count per viewer) were decided by me while building, because the rules needed them. They are small and follow from the ADR, but they are yours to overrule.
